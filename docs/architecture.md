# Architecture decision: static first

React + TypeScript + Vite render an entirely client-side interface. JSON is the version-controlled source of truth and is imported into the production bundle as a build-time search index. The reviewed static portfolio does not require a search service or a generated duplicate index. Search is deterministic and case-insensitive; exact matches sort first. Family preferences rank only within the same decision class and cannot rescue failed hard requirements.

The app uses hash routes (`#/product/<encoded PID>`), which survive GitHub Pages deep links without a 404 rewrite. Requirements and exact-PID hardware selections persist locally when browser storage is available, and are reevaluated when loaded. Unrecognized module identities stay unknown. Comparison IDs also persist; malformed/obsolete base IDs are discarded. Downloads remain available without storage. CSV uses UTF-8, quoted cells and formula neutralization. There are no trackers, third-party fonts, login, cookies or mandatory runtime network calls. Official references open in a new tab with `noopener noreferrer`.

The root English dictionary is in `src/lib/i18n.ts`; navigation and shared strings are separated. Full PT-PT translation and extraction of remaining component copy are future work. Device art is an original schematic representing a category; it is not evidence of chassis construction or a port layout.

Supported matching inputs include physical ports, dedicated copper/fixed fiber/SFP interfaces, dedicated uplinks, port rates, PoE budget/standard, DIN rail, Cyber Vision, firmware, management mode, lifecycle context and family preference. Explicitly selected compatible modules extend these metrics while base specifications remain separate. A component BOM records exact selected PIDs; transceivers, PSUs and complete network design remain outside this model. Unknown evidence, unsupported version formats and unverified coexistence stop a verified fit. No inferred port expansion, price, availability or license activation is claimed.

Tests exercise deterministic rules, provenance failures, dates, IDs, search, contradictions, export and browser interactions. Browser tests use actual committed records for browse flows and intercepted synthetic fixtures to isolate comparison plumbing. A valid schema does not establish that a vendor statement is true. Review has to inspect the original source and applicability.

Phase B retains this architecture. Family filtering and a 24-card initial page keep the larger portfolio usable. Product pages add a documentation library, a mode/context compatibility matrix, lifecycle warnings and commercial checks. Family references expose explicitly scoped evidence even when exact ordering identity is unresolved, without adding those research candidates to recommendations.

`configurations.ts` evaluates exact hardware fit, runtime support, slot use, shared PoE and supply requirements before composing findings with existing base rules. It calculates component/proposed/mode-countable capacity without mutating stored inventories. Planned Meraki support cannot contribute a positive module match. `ExpansionModules.tsx` exposes the same deterministic evaluation in detail and comparison views; BOM/JSON exports use the full result, including base lifecycle and security conditions. See [expansion coverage](expansion-modules.md) for source boundaries. No cabinet simulator or assembled geometry is implemented.

The optional audit is now a two-job GitHub workflow: public observations run read-only; a separate writer proposes only immutable history in a PR. The existing Pages workflow and required reviewer are unchanged. See `docs/phase-b-evidence.md` for release-specific findings and unresolved boundaries.
